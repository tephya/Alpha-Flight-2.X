## 记录一：RTOS基础架构搭建

- 确定FreeRTOS下用`NVIC_PRIORITYGROUP_4`，`configMAX_SYSCALL_INTERRUPT_PRIORITY=5`红线；发现并补上EXTI line4（IMU1）、EXTI line[15:10]（IMU2）未启用的遗漏。

- VSCode+Keil Assistant环境调通：`.vscode`需放MDK-ARM子目录、`compilerPath`指向真实armcc.exe、`intelliSenseMode`设`linux-gcc-arm`。

## 记录二：旧架构解读 → 新架构文件级迁移

- **核对发现此前笔记记录严重失实，推翻重新以源码为准**：不存在`EXTI9_5_IRQHandler`（实际是TIM7软件定时+DMA+软中断分层）；ELRS不是中断驱动（实际DMA循环+主循环轮询，可原样保留）；`Motor.c`是死代码；DSHOT是单路DMA burst非四路独立；双IMU冗余在旧代码里完全没有物理链路；旧代码从未真正启用IMU的INT1中断。
- **教训**：分析笔记/口头结论不能替代源码本身，关键判断要回源码核实。
- IMU朝向确认新板与旧板一致，ax/ay、gx/gy互换的hack可直接复用。
- GPS PPS确认不接入EXTI，气压计硬件损坏跳过，磁偏角暂不接入。
- Task/Queue实际命名以CubeMX截图为准（`Task_FlightCtrl`等，与记录一文字记录的命名不同）。
- 定下"单写单读用共享volatile结构体，跨Task常规数据走Queue"这条区分规则。
- 发现CMSIS-RTOS2没有原生`xQueueOverwrite`，定案统一用"查满→丢弃旧值→Put"模式实现覆盖式写入。
- 双IMU冗余方案首次定案：档位二真正主备切换、快切慢回（5帧/200帧）、不做零偏补偿平滑。
- 分层封装规范成型：bsp层内部static+CopyTo，坐标系hack消化在bsp层。
- 踩坑：`MagData_t`/`MAG_Data_t`混用；`freertos.c`里手写了跟CubeMX保留名重复的函数导致`multiply defined`。

## 记录三：双IMU冗余全链路打通

- IMU1引脚在记录二被误改为INT1=PC4，本次经实机验证改回PA4（文档本身章节间自相矛盾，以实测为准）。
- ODR从旧固件1600/3200Hz改为800Hz，统一匹配控制环频率。
- 驱动文件从计划的`bsp_icm1`+`bsp_icm2`两文件合并成一份`bsp_icm42688.c`+`IcmInstance_t`枚举参数化。
- `Task_IMU2_RDD`确认不设独立Task，判定逻辑直接内嵌`Task_FlightCtrl`。
- ICM-42688P-HYX手册关键信息确认：无`REG_BANK_SEL`，`INT_CFG2`没有独立锁存/脉冲模式字段。
- **Bug 1：旧测试代码逐字节独立SPI事务导致"撕裂读"**，新架构burst读天然规避。
- **Bug 2：`osFlagsWaitAny`几乎不可能同时捕获两路独立时钟的DRDY**，导致早期"两路都到齐才做交叉比对"的写法形同虚设，改成无条件每次循环执行交叉比对。

- IWDG从项目最早期就使能但从未真正喂狗，调试期间断点暂停触发过复位、一度被误判为代码逻辑问题。
- 六轴交叉比对阈值首次测定，标记为PROVISIONAL待重测。

## 记录四：控制链打通 + IWDG/ARM前置设计 + 代码审查

本次主线：从IWDG喂狗设计开始，一路做到PID/控制器/姿态融合/ELRS/GPS Home全部打通，中间交替做了两轮完整代码审查。

### IWDG设计

- 明确喂狗权限只属于`Task_IwdgFeed`，其余Task只上报`g_heartbeat`时间戳，不直接碰`HAL_IWDG_Refresh`——否则等于没有真正的多任务联合监控。
- 心跳超时阈值50ms（FlightCtrl标称周期1.25ms×40倍留裕量，经验默认值非精确推导）。
- 确认FlightCtrl循环本身有阻塞窗口（`osEventFlagsWait`），不会长期占死CPU饿死低优先级任务。

### 分层与命名问题（反复出现，是本次最大的一类坑）

- `MagData_t`一度被建议放进`app_shared_types.h`，后确认应归属`bsp_qmc5883.h`（数据有唯一生产者的类型，归属生产它的bsp模块）。
- `RCChannelData_t`同样的问题重演了一次：先是在`bsp_elrs.h`里另起一个大小写不同的`RcChannelData_t`，跟`app_shared_types.h`里的`RCChannelData_t`并存，`app_rc_link.c`混用两个名字导致潜在的结构体不匹配；后确认`RCChannelData_t`定义应完全归属`bsp_elrs.h`，`shared_types.h`不留副本。
- **教训**：这类"同一份数据被两个几乎同名的类型定义"的坑会反复出现，本质是没有先问"这份数据的唯一生产者是谁"就先动手写类型定义。以后新增数据类型前，先确认归属再写。
- `fc`（`FlightControl_t`）一度按`g_imu_health`同款处理成`extern volatile`直接暴露，后改为`static`+`FlightControl_CopyTo()`——区别在于`fc`字段多、体积大，直接暴露会带来撕裂读风险，`g_imu_health`那几个标志位不存在这个问题，不能套用同一个模式。

### PID/控制器/姿态融合（`alg_pid`/`alg_controller`/`alg_mixer`/`alg_attitude`）

- 旧代码`controller_angle.c`/`controller_rate.c`/`flight_controller.c`里的Mixer、PID、映射函数评估后判定质量扎实，原样移植，只做文件合并整理，不重写逻辑。
- `alg`层判据明确：不碰HAL、不碰RTOS对象、不知道数据来自哪颗传感器，函数参数按物理意义命名（`roll_rate`而非`gx`），避免向外暴露硬件相关命名。
- **朝向修正的定位问题，讨论了两轮才收敛**：最初以为需要在`app_flightctrl.c`里加一个独立`IMU_ToNED()`统一转换点，后来查实旧代码的真实做法是"换轴在bsp驱动层做、取负在两个控制器调用点分别做"，两者不是一回事，不能合并处理，此前的`IMU_ToNED`方案被撤回。
- 撤回`IMU_ToNED`后又留下一次残留Bug：`App_FlightCtrl_Task`循环体里保留了当初为`IMU_ToNED`方案准备的局部变量（`active_gy`已取负），同时`FlightControl_Update`调用又在内部再取一次负，构成双重取负（等于没取负），被发现纠正。
- `YawHeadingHold_Update`过零点处理不对称（`+=180.0f`应为`+=360.0f`），代码审查发现。
- `Map_Pitch`当前实现丢了旧代码的负号，跟另外两处（角度环/角速度环入口的取负）之间的关系没有验证清楚，判定为**不能靠猜删除**，需要物理测试（手动倾斜机身对照符号）验证后才能定案，避免PID闭环极性反转导致炸机。

### ELRS/RC链路

- 旧`elrs.c`核实后发现**完全没有失联检测**，`crsf_data`可能陈旧数分钟仍被当作当前值使用，新架构补上`link_ok`字段。
- 移植时**CRC8校验范围写错**（循环从i=0而非i=2开始，把Sync/Len也算进了校验），会导致每一帧CRC校验必然失败、通道数据永远收不到，代码审查中发现，是本次最严重的一处bug。
- Packet Rate确认为150Hz后，据此定案失联阈值70ms、`Task_RC_Link`轮询周期4ms。
- 讨论过是否要把DMA环形缓冲区"追赶循环"理解为出错后会空转——纠正：循环迭代次数只取决于两次poll之间的新增字节数，跟解析是否成功无关；真正的风险是两次poll间隔过长导致128字节缓冲区被覆盖丢数据，不是空转变慢。

### GPS Home

- 最初讨论过"是否要把搜星流程从Task里抽出来放main.c阻塞执行"，回到旧架构那种线性流程——判定不可行：会让IWDG防护、RC失控保护、指示灯反馈在搜星期间全部停摆，且现有`Task_Nav`方案已经用非阻塞方式解决了同样的问题，没有理由倒退回阻塞模型。
- `NAV_CMD_SET_HOME`最初设计成"任务入口发一次"，后发现这样只会尝试一次、大概率因为卫星数不够而失败且不会重试，改成主循环里持续检查`s_home_valid`、未成功则重试，命令队列改为只服务于以后需要外部显式触发重新记录Home点的场景。
- `NavState_t`组装时经纬度被多缩放了一次1e7倍（`bsp_gps.c`的`nmea_to_fixed`已经输出定点整数，`app_nav.c`又乘了一次1e7f），代码审查发现。

### 双IMU冗余代码审查中发现的问题

- `Health_RecordGood`里"快切慢回"的回切阈值判断用错了常量（写成`SWITCH_AWAY_THRESHOLD`，应为`SWITCH_BACK_THRESHOLD`），导致备用IMU只需5帧健康就会被标记可用，而不是设计要求的200帧——这条是本次第二严重的bug，直接削弱了"快切慢回"机制本身。
- 补充设计了"双路失效"的处理：备用也不健康时不再无意义切换，冻结`active_imu_sel`、置`dual_fault`锁存标志，交给下游自行判断，本层不越权做保护决策。

### 其他代码审查发现的零散问题

- `g_heartbeat.flightctrl_last_tick`赋值一度用了`osKernelGetSysTimerCount()`，跟`Task_IwdgFeed`那边读取用的`osKernelGetTickCount()`不是同一时间基准，会导致超时判定失效（要么永远超时要么永远不超时），已改统一用`osKernelGetTickCount()`。
- `g_heartbeat.filghtctrl_last_tick`字段名拼写错误，编译不过。
- `alg_pid.h`一度包含了`stm32f4xx_hal.h`，违反alg层不碰硬件头文件的规矩，改用`<stdint.h>`。
- `bsp_qmc5883.h`里出现过`static`函数声明（`QMC_Raw2Gauss`），头文件不该放内部链接声明，已删除，只保留在`.c`内部。
- `M_PI`在部分工具链下`<math.h>`不提供，需要`#ifndef`保护自行补充定义，只在用到的文件里加一处，不重复。
- `FlightControl_CopyTo`函数体一度是`(void*)out;`的无效写法，没有真正做拷贝，代码审查发现并改为整体赋值。

### 元话题：记录格式本身的评审

- 早期按时间线堆料、层层覆写标注的格式，读起来有点懵、有点不舒服。
- 评审结论：问题在于"当前正确状态"和"变更过程"混在同一份文档、同一层级里，读者要自己做时间线合并才能知道现在到底是什么样；细节参数和架构决策没有视觉分层；纠错复盘占用篇幅冲淡正文。
- **改版方案**：拆成《当前状态》（只写现在生效的结论，不出现"以xx为准"字样）+《变更与踩坑记录》（按时间顺序，服务于"想知道为什么"的场景）。本文档即为这次改版后的产物，后续按"维护和更正现有内容，而非持续堆料"的原则更新。

## 记录五：DSHOT/ARM状态机/电源监控/SystemReady全量接入 + 上电死锁复发排查 + 黑匣子重构

### DSHOT输出（`bsp_dshot.c`）

- 闸门归属定案：`bsp_dshot`是纯执行层，不做ARM判断、不做48偏移映射，只管把传入的payload编码发出去；解锁与否由调用方（ARM状态机）决定传0还是传`Mixer`值+48。
- Disarmed状态下明确要求**持续发送(0,0,0,0)**，不是"不解锁就不调用发送函数"——旧代码"不调用"的写法会导致电调长时间收不到帧流，可能触发电调自身的失控保护/报警，改为"闸门体现在传什么值，不是调不调用"。
- DMA burst缓冲区元素类型必须是`uint16_t`（跟`hdma_tim1_up`的`MemDataAlignment=DMA_MDATAALIGN_HALFWORD`绑定），不能因为`HAL_TIM_DMABurst_MultiWriteStart`接收`uint32_t*`就把缓冲区声明成`uint32_t`，否则实际发送的半字数据会错位。
- `MX_TIM1_Init`只做了Base/PWM/BreakDeadTime配置，没有真正启动输出，`BSP_DSHOT_Init`里补了四通道`HAL_TIM_PWM_Start`（对Break型定时器会顺带使能MOE位）。
- Mixer输出上限`MIXER_OUTPUT_LIMIT`定为1352（不是DSHOT满量程2047），是电流保护的刻意选择（避免烧毁4in1 65A电调板），`bsp_dshot`层不对这个上限做二次拉伸映射，直接+48送出。

### ARM状态机（`app_arm.c`）

- 落点：跟`Task_FlightCtrl`同级、不单开Task，理由类比双IMU冗余当初否掉`Task_IMU2_RDD`独立Task的判断——所需的RC数据和倾角数据都已经在`Task_FlightCtrl`循环里现成可用，拆出去除了引入信箱抢占问题外没有收益。文件形态是模块（`app_arm.c`），被`Task_FlightCtrl`每循环调用`Arm_Update()`。
- 状态暴露方式：跟`g_imu_health`同规矩，`extern volatile ArmState_t g_arm_state`直接读，不用CopyTo（单字节枚举，撕裂读风险可忽略）。
- 解锁判据：RC ARM键 + 低油门 + 倾角<30°（`ARM_TILT_LIMIT_DEG`，起飞前水平检查用），且`SystemReadyEventGroup`五个bit全部就绪。
- 正常落地退出：RC DISARM键+低油门，持续满6秒（`ARM_DISARM_HOLD_MS`），用时间戳判断而非旧代码那种"每2秒轮询、连续3次"的粗糙debounce——旧写法是配合旧代码阻塞式主循环的凑数方案，新架构800Hz连续循环下改成"条件首次满足时记录时间戳，之后每帧比对`osKernelGetTickCount()`差值，条件一旦中断就清零重来"。
- 紧急disarm（飞行中）：`dual_fault`（双IMU失效）、`voltage_fault`（持续低压）、倾角保护触发，三者任一立即disarm，不走6秒debounce——这三者代表的是持续性故障或已失控，跟"正常收桨"不是一回事。
- **倾角保护阈值不能跟解锁前置检查的30°共用**，这是本次一次重要的设计澄清：30°是起飞前地面水平检查的门槛，飞行中哪怕温和转弯、抗风纠偏都会自然超过30°；倾角保护要的是"判定已经失控/翻转"，两者物理意义不同。综合遥控目标角映射（±20°→后改±30°）、风扰下的实际姿态角可能超过30°这两点，倾角保护阈值定为**60°**（经验取值，留出约一倍于正常机动余量，同时离90°"基本等于翻了"还留足反应空间），独立函数`TiltProtection_Check()`实现，不与`Arm_TiltOk`（30°）混用。
- 双路IMU失效（`dual_fault`）与ARM状态机联动：Disarmed时`dual_fault`置位禁止解锁（倾角判据本身依赖IMU数据，数据不可信则无法验证解锁前提）；Armed时`dual_fault`置位立即disarm。

### 电源监控（`bsp_power.c` + `app_power_monitor.c`）

- CubeMX的`hadc1`是Scan模式两通道：Rank1=VBAT（PC0/ADC_CHANNEL_10），Rank2=电调电流检测（PC1/ADC_CHANNEL_11，`CRT_Pin`）。这次只接VBAT判断逻辑，电流这一路只读出存着，不参与任何判断。
- 电流不接入的理由是实测数据支撑的决策，不是偷懒：旧代码`Protection_Update()`里过流阈值44A是针对330mm机架/4in1 65A电调板配的经验值，实际配置是10寸机架/2212 1100KV/APC1050两叶桨/2200mAh 4S，实测780油门杆最大电流约12A，离44A/65A都远，且旧代码"Kp*error"这套比例限流环节的Kp调参依据不明，不能凭空替编一个没有依据的控制参数，留到以后专门测试再做。
- 低压阈值13.2V（对应4S电池单片3.3V下限，换电池节数改这一处常量即可）；`VOLTAGE_OK`置位加了迟滞（回升到13.5V才重新置位，防止临界点抖动反复置/清）；连续5次(~500ms@100ms周期)低于阈值才确认`voltage_fault`，滤掉大机动瞬时压降造成的误判——`Task_PowerMonit`已经是独立FreeRTOS Task，100ms周期，跟旧代码"跟倾角检测共用100ms tick"的周期取值一致但执行方式完全独立。

### SystemReadyEventGroup 五个bit全部接线

- `HOME_VALID`（`Task_Nav`）、`RC_LINK_OK`（`Task_RC_Link`，直接复用`bsp_elrs.c`已算好的`link_ok`）：直接跟对应的既有状态变量同步置位/清位，逻辑简单。
- `IMU_HEALTH_OK`（`Task_FlightCtrl`）：镜像`!g_imu_health.dual_fault`，每循环持续更新。设计澄清：这个bit只在`Arm_Update`的Disarmed分支（解锁前置条件）被检查，Armed期间不重复检查——单IMU故障切换（冗余机制正常工作）不会置`dual_fault`，不影响继续飞行；只有两路都坏时`dual_fault`才置位，这条路径在Armed分支由独立的紧急disarm检查兜底，不依赖这个bit。
- `MAG_OK`（`Task_Nav`）：手册排查后确认，QMC5883的自检功能（寄存器0x0B的SELF_TEST位）不适合做运行时持续检测——自检会让芯片跳出Continuous Mode进入Suspend，测完需要重新配置才能恢复连续输出，跟`Task_Nav`每20ms要拿新数据的需求冲突，只适合开机一次性诊断（这次未接入，留待专门的QMC自测环节）。改用状态寄存器0x09的**OVFL位**（任一轴数据溢出，超过当前±8G量程即置位）+ I2C读取是否成功，两者都满足才判`MAG_OK`。
  - 排查过程中确认了一个容易搞混的点：OVFL的"±30000 LSB"判据不是int16的硬件上限，是跟当前配置量程绑定的——四档量程(±30G/±12G/±8G/±2G)乘各自灵敏度都恰好等于30000，本质是"实测磁场强度超过当前量程上限"，不是巧合。
- `VOLTAGE_OK`（`Task_PowerMonit`）：见上一节。

### 遥控通道映射角调整

- `Map_Roll`/`Map_Pitch`从±20°上调到±30°。原因：这是遥控能要求到的目标角权限上限，跟PID调参是两件独立的事——哪怕PID调到最优，只要映射角上限设低了，摇杆打满也没法要求更大姿态角去抵抗风扰，"控制权限不够"和"控制器没调好"不能混为一谈。10寸户外机型风扰下实际姿态角容易触及±20°上限，上调后留出更多纠偏空间，同时离60°倾角保护还留出足够安全边际。

- **教训**：`osEventFlagsNew()`创建的事件对象本身默认就是清零状态，这行`Clear`除了在特定时序窗口下误吞一次关键真实事件外没有任何实际作用，纯属多余代码带来的隐蔽bug，删除即为正确修复而非权宜之计。
- 两处改完（`ICM_ClearDataReadyLatch`长度参数13、删除多余的`osEventFlagsClear`），多次重新烧录验证，"忽好忽坏"现象消失，IMU1/IMU2稳定工作。

## 记录六：黑匣子/提示系统全量实现 + SD卡DMA疑难杂症排查（长篇）

### SD卡底层重写（`bsp_sdcard.c`，HAL+DMA版）

- 从旧架构标准库风格的`TFCARD.c`重写成HAL版本，DMA用`HAL_SPI_TransmitReceive_DMA`统一处理读写，不再像旧架构那样"读逐字节阻塞、写才用DMA、DMA的RX侧还是个不递增的1字节丢弃桶"这种不对称设计。**这个决定后来被证明是本次后半段一系列疑难问题的根源**，详见下文"DMA约10秒卡顿"。
- `SD_SPI_SetSpeed`旧架构里的固定速度值（2.625MHz，`SPI_BaudRatePrescaler_16`），改成`BSP_SD_SetSpeedFast()`运行时用`HAL_RCC_GetPCLK1Freq()`动态算出不超过2.625MHz的最高档位，不硬编码分频值，避免时钟树跟假设不一致时算错速度。
- 遇到armcc对`__packed`结构体成员数组隐式退化成指针传给`memcpy`会报`argument incompatible with void *restrict`，需要显式`(void *)`强转——纯C语义层面的编译器较真，跟逻辑无关。

### 黑匣子实现（`bsp_blackbox.c` + `app_blackbox.c`）

- 双缓冲+信号量设计，帧格式定案（MAGIC同步头+type+内容，见《项目当前状态》十一）。
- 生产端调用点全部接线：`app_flightctrl.c`（Motion帧）、`app_arm.c`（ArmChanged）、`app_imu2_redundancy.c`（DualFault/ImuSwitch）、`app_power_monitor.c`（VoltageFault）。
- **文件生命周期设计经历过一次重大重构**：最初是Task启动时立即`BB_Init`开一个文件、一直用到关机，讨论后改成"每次解锁开新文件、上锁关文件"（对齐Betaflight blackbox一次飞行一份记录的惯例），再讨论后进一步改成"开机不自动建文件，纯懒加载，等第一次真正解锁才建"——避免地面静置期间凭空产生一个空文件。
- **`s_ctrlEvt`死锁bug**：文件生命周期改成懒加载后，`BB_RequestNewFile()`/`BB_RequestClose()`/`BB_PollControlRequest()`依赖的`s_ctrlEvt`事件对象，原本创建代码放在`BB_BufferInit()`里，但`BB_BufferInit()`现在只有`BB_Init()`成功后才会调用，而`BB_Init()`又要等`BB_RequestNewFile()`触发——形成死循环，`s_ctrlEvt`永远是`NULL`，往`NULL`对象上置位/等待，信号直接丢失。**修复**：拆出独立的`BB_ControlInit()`，在`Task_Blackbox`一开始、进入任何等待循环之前调用一次，跟文件是否已打开彻底解耦。
- 顺带修了`BB_BufferInit()`里`s_dataReadySem`创建代码曾经在某次代码回退中丢失过`if(NULL)`保护，导致每次重新解锁都会新建一个信号量对象、旧的没人释放——补回保护。
- `app_blackbox.c`主循环里出现过`&&`和`&`用混（`if(ctrl && BB_CTRL_CLOSE_REQ)`应为`&`）+ 大括号范围写错导致`NEWFILE_REQ`判断跑到`(int32_t)ctrl>=0`保护范围之外，几乎每次循环都会误触发重建文件——已修复。同一批还有一处`(uint32_t)ctrl>=0`（恒真，应为`(int32_t)`）的typo。

### 提示系统全新实现（`bsp_buzzer.c`/`bsp_led.c`/`app_indicator.c`）

- 蜂鸣器/LED/优先级报警状态机全部是本次新增模块，设计过程见《项目当前状态》十三，不再重复。
- **音量问题**：50%占空比+谐振频率是"最大音量"配置，压电片被驱动效率最高，声音大得离谱；改成可调占空比（`BUZZER_DUTY_PERCENT`），从15%开始试。
- **两版节拍查表写法的取舍**：先用了C99指定初始化器`static const IndicatorPattern_t s_patterns[] = { [EVT_ARMED]=..., ... }`这种数组下标绑定的写法，armcc(V5.06u7)对这个语法支持不完整导致编译报错（"表达式必须包含算术类型"，根子是数组声明本身解析失败），改成按枚举声明顺序的普通数组初始化——但这个方案有"顺序脆弱"的隐患（谁在枚举中间插入新值都会导致错位，且不会编译报错）；最终改成`switch`按事件名字（`case EVT_XXX:`）分发，彻底摆脱位置依赖，唯一代价是漏加`case`不会编译报错、只会运行时走`default`返回`NULL`（"不会错着响，只会不响"，比数组版本"错位后响成别的事件"更安全）。**这次教训**：`app_indicator.c`一度出现过"两套查表逻辑并存"的疏漏——`Indicator_GetPattern`（switch版）算出来的`pat`只用来判断`NULL`，实际播放时却绕开它、直接用旧的`s_patterns[evt]`数组，导致switch重构等于白做，播放的还是旧数组（且两版数据内容还对不上，是"蜂鸣器节拍听感对不上预期"这个体验问题的根因）。已改成播放逻辑统一用`pat`，旧数组删除。
- 持续报警设计：`EVT_RC_LOST`/`EVT_CRITICAL_BATTERY`/`EVT_IMU_FAULT`三个安全关键事件明确要求改成"故障持续存在就按固定间隔重发"，其余保持跳变沿单次提示。重发间隔取值原则：略大于自身节拍播放时长，避免队列（深度8）被同一事件灌爆。

### `is_initialized`标志位锁死bug（ST官方`diskio.c`生成代码本身的问题）

**排查过程本身很曲折，最终发现是ST自己生成的胶水代码的bug，不是本项目引入的**：

- 最初表现是`f_mount`返回`FR_NO_FILESYSTEM`，一路查到`user_diskio.c`的`USER_read`/`USER_write`是从未被填写过的空骨架（`return RES_OK`不做任何真实数据读写），先补全这层。
- 补全后仍然不稳定，观察到"只有完整走几轮MCU复位才有~98%概率初始化成功，纯软件重试没用"这个规律，据此深挖到`diskio.c`（ST生成，非`user_diskio.c`）里`disk_initialize`的`is_initialized[pdrv]=1`在调用真正的`USER_initialize()`**之前**就无条件执行——第一次握手失败后这个标志位永久锁死，之后`App_Blackbox_Task`里的`while(BB_Init()!=0){osDelay(500);}`重试循环全部被短路，`disk_initialize`直接返回一个从未被赋值过的`RES_OK`糊弄上层。**修复**：只有真正握手成功才置位`is_initialized[pdrv]`。这个修复被验证有效——后续测试里软件重试循环能自主从`0xF4`这类失败响应恢复到`0x01`成功，不再需要手动复位。
- ⚠️`diskio.c`本身是CubeMX可能重新生成的文件，这个补丁没有`USER CODE`保护区包裹，重新生成代码会被覆盖，需要记得重新打。

### CMD0/CMD17/CMD24缺少真实延时（对齐旧架构线索排查出的问题）

- 关键线索：这张SD卡表现出"需要真实流逝时间才能从上次遗留的半截状态里自行恢复"的特性，断点暂停能让CMD0稳定成功（人为注入了真实时间）。
- 复查代码发现CMD0重试循环（10次）完全没有延时，跟同一文件里ACMD41循环（有`osDelay(1)`）不对称；补上`osDelay(2)`后配合"握手开始前先`osDelay(10)`"，CMD0成功率明显改善。
- 用同样思路排查CMD17（读）/CMD24（写）的命令重试循环，发现同样没有延时，同样补上`osDelay(2)`。
- 旧架构对比：`TFCARD.c`的CMD0重试循环里，`SD_CS_HIGH()`宏本身自带1个dummy byte，循环体里还**额外多发一个**——这是旧架构独有、其余命令没有的写法，最初怀疑是这个"多一个时钟"的差异导致的，尝试对齐补上后effect有限，后来证明"真实延时"才是更关键的因素，"额外dummy clock"这个差异保留但不是主因。

### DMA传输约10秒卡顿（本次最大的未解决问题，记录八解决）

排查历经多轮理论提出与证伪，完整过程记录如下，避免下次重复踩同样的坑：

1. **最初怀疑NVIC优先级违反FreeRTOS红线**（`HAL_SPI_TxRxCpltCallback`在ISR里调`osSemaphoreRelease`，如果ISR优先级数字小于`configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY=5`就是违规）——查`dma.c`实际配置，`DMA1_Stream3`/`Stream4`都是优先级8，在安全范围内，**证伪**。
2. **怀疑信号量被上一次超时后迟到的完成回调污染**（超时返回后DMA仍在后台跑，之后真正完成时多释放一次没人消费的信号量，被下一次调用误当作"自己的"完成信号提前放行、读到脏数据）——加了"发起传输前先非阻塞排空一次信号量"的双重保险，问题依旧存在，**基本证伪**（或者说这条不是主因，即使问题存在也解决不了核心问题）。
3. **尝试超时后主动`HAL_SPI_DMAStop`叫停**——结果导致几乎每次都直接失败（`-2`/`-3`），怀疑这个函数把SPI外设本身也关掉了，牵连了大量阻塞式单字节收发（CMD交互、CRC读取）。**已撤回，改为只保留排空信号量这一步**。
4. **怀疑测量本身失真**——用`osKernelGetTickCount()`测出约5秒到10秒不等的耗时，数字本身可疑（过于集中，像是某个确定性机制而非随机硬件抖动），且怀疑`SysTick`被某个高优先级活动饿死导致tick计数跟真实时间脱节。用DWT硬件周期计数器（不依赖任何中断/调度，完全独立）交叉验证，两种测量方式数值高度一致（约10.4~10.5秒），**排除了测量误差这个可能性，确认延迟是真实存在的**。
5. **一次测量方法本身的疏漏**：曾用共享的PB9 LED做"点亮-熄灭"标记，肉眼验证延迟真实性，后来意识到这颗LED同时被`app_indicator.c`的报警节拍控制着，两边可能互相打架导致观察结果不可靠——已改用DWT方案替代，不再依赖这颗共享LED做诊断。
6. **确认`g_sdDmaCpltCount`（完成回调触发次数）跟调用次数一致**——排除"中断压根没触发"这个可能性，问题性质从"链路断了"收窄成"传输本身真的很慢"。
7. **确认`hspi2.State`大部分时候是`HAL_SPI_STATE_BUSY_TX_RX`、`hspi2.ErrorCode`全程为0**——排除OVR等SPI错误标志的可能性，卡在"忙碌"是真实的忙碌，不是错误状态被卡住。
8. **决定性实验**：把512字节数据段的DMA传输临时换成逐字节阻塞轮询（新增`SD_SPI_Blocking_Transceive`），实测稳定4ms完成，`f_mount`直接成功。**证实问题精确锁定在"DMA驱动的连续全双工突发传输"这一种模式，不是命令交互/握手时序/FatFS逻辑的问题**。
9. **回溯为什么旧架构没暴露这个问题**：旧架构的"读"从未真正走过DMA（纯阻塞轮询），DMA只用在"写"，且写的DMA配置里RX侧是个固定1字节不递增的"丢弃桶"（纯粹为了吸收全双工模式下的无意义回传字节），从未验证过"TX/RX两侧都是真实512字节递增缓冲区的DMA全双工突发"这种用法——**这次不是旧架构验证过的东西在新架构上倒退了，是新架构第一次真正把这种用法跑起来，暴露出了一个可能是这张SD卡本身固有的、旧架构从未触及过的短板**（此判断后被记录八推翻，真正根因见记录八）。

- **当时的状态**：读写两侧的512字节数据段临时切回阻塞方式（`SD_SPI_Blocking_Transceive`），工程上可用，但不满足于止血，计划继续深挖DMA为什么在这张卡上不稳定，用逻辑分析仪抓SPI2的SCK/MOSI/MISO/CS波形对比阻塞与DMA两种模式。`SD_SPI_DMA_Transceive`函数本体保留在代码里，未被调用，未清理。

### RC通道数据冻结问题——已解决

- 先核对了`ARM_RC_CHANNEL_SWITCH`/`ARM_RC_CHANNEL_THROTTLE`两个宏定义的索引，一度怀疑CH4/CH5搞混导致索引差1，后经核实遥控器编号规则（CH1起、数组[0]起，CH5=SD=channels[4]），两个宏定义本身没有问题，这条排查方向作废。
- Live Watch一度对`s_rc_data`/`s_rc_data.channels[]`报"cannot evaluate"，排查过文件限定符语法、Rebuild All、优化等级、Periodic Window Update设置，最终确认是Keil Live Watch本身不支持直接watch结构体/数组整体，改为逐个watch标量成员（如`channels[4]`）后正常。
- 断点设在`Arm_SwitchOn`函数体内，观察到"只有首次命中时数据是新的，之后反复命中都是同一份旧数据，期间拨动遥控器开关也不变"，缩小了范围但还未定位到具体环节。
- 关键突破：在`ELRS_Poll`里`__HAL_DMA_GET_COUNTER(huart2.hdmarx)`这一行断点，观察到`counter`在reset后从128(0x80)变为0（代表DMA收满一轮128字节），但之后再也不变化——不是正常circular模式该有的持续循环递减/重载行为。
- **根因**：`usart.c`里`hdma_usart2_rx`的DMA Mode配置为`DMA_NORMAL`，收满`DMA_BUF_SIZE`(128字节)后DMA自动停止，不会重新装载继续接收。CubeMX里UART的DMA配置截图仅显示Stream分配列表（Request/Stream/Direction/Priority），未显示Mode字段，需要点开该行的Parameter Settings子标签页才能看到并修改。
- **修复**：CubeMX里把USART2_RX对应DMA Stream的Mode从Normal改为Circular，重新生成代码，验证有效，`s_rc_data`此后能持续正常刷新。
- 顺带确认：SPI2（SD卡）的DMA Mode本身应保持Normal不变——SD卡是"每次收发固定512字节、一次性传完即停"的场景，跟USART持续接收未知长度数据流的场景不同，Normal在SD卡这里是正确选择，不能类比套用Circular。
- 顺带确认：`ff.c`/`diskio.c`这类FatFS中间件文件，不受CubeMX的`USER CODE BEGIN/END`保护区机制保护——CubeMX重新生成代码时，如果判断该中间件文件需要更新，会整份覆盖，不会解析保留区内的用户代码。此前给`disk_initialize`打的补丁不能靠加`USER CODE`注释来避免被覆盖，只能靠自己记录、每次CubeMX生成后手动`diff`核对是否被冲掉。

### SD卡DMA传输问题——长时间深入排查，记录末尾未解决，留下明确的下一步方向

**排查方式的转变**：本次早期沿用上一次止血用的阻塞版本先排查了ELRS问题，之后切回DMA版本继续深挖SD卡问题。全程综合使用了断点+Watch窗口寄存器读取、逻辑分析仪波形抓取、独立最小化测试环境（新增`app_sdtest_demo.c`）三种手段交叉验证。

**逻辑分析仪波形排查过程**：

1. 最初只测单线SCK，因为没有正确框住完整的传输窗口（默认采集时长太短），测出的"频率"数字（100Hz级别）是无意义的假象，排查后确认是采集窗口时长不够（改成50s+窗口后才框住完整周期）。
2. 单独抓SCK：观察到大周期约10.2~10.35秒，内部又能看到"每帧5.1~5.15秒"的活跃区间，活跃区间内部进一步放大，能看到帧头2字节+帧尾约39字节间隔约3μs（正常速度），中间大段字节间隔约10ms（异常龟速）。
3. 单独抓CS：观察到CS一次连续拉低约9.8~10秒，之后拉高约200~500ms，周期性重复。
4. 同时抓CS+SCK两线：确认SCK的活跃窗口紧跟在CS拉低之后开始，但活跃窗口结束后CS并不会立刻抬起，还会继续保持低电平约5秒的完全静默期，之后才真正抬高——之前对"5.5秒空白"的位置理解有过反复（一度怀疑是两次调用之间的间隔，后修正为同一次CS周期内部的静默）。

**断点/寄存器排查过程**（在逻辑分析仪确认框架的基础上，用寄存器读数逐步收窄范围）：

1. `hspi2.Instance->CR1=0x035C`：确认SPI2时钟配置正确（BR=÷16，PCLK1=42MHz，实际2.625MHz，与设计值吻合，`RCC`时钟树图核实过PCLK1确实是42MHz，不是`main.c`的`SystemClock_Config`配置有误）。
2. `NDTR`观测：一度用多次自由运行+手动Halt的方式采样`hdma_spi2_rx.Instance->NDTR`，发现有实际递减，一度以为传输在正常但缓慢地进行；但这种离散采样方式的可靠性后来被质疑（存在采样点碰巧落在活跃窗口的偏差风险）。
3. `DMA_PRIORITY_VERY_HIGH`实验：把`hdma_spi2_rx`/`hdma_spi2_tx`的`Init.Priority`都改到最高优先级，重新验证`hdma_spi2_rx.Init.Priority`寄存器确认改动生效（`DMA1_Stream3->CR`的PL字段确实是11），但现象完全没有改善，排除了"DMA被总线仲裁饿死"这个方向。
4. 排除`Task_FlightCtrl`等高频Task干扰：先尝试在`App_FlightCtrl_Task`里临时注释掉姿态解算等重运算部分（只保留`ImuRedundancy_Update`+`Arm_Update`），耗时依然是10.27秒左右，无变化；进一步注释掉`ImuRedundancy_Update`（只留`Arm_Update`+`osDelay(1)`轮询），此时意外触发了`g_arm_state`反复横跳（ARMED-DISARMED-ARMED反复跳变，伴随蜂鸣器狂响、黑匣子反复重新握手SD卡），排查后确认是这次简化改动破坏了`Arm_Update`依赖的`fc.roll_meas`/`fc.pitch_meas`/`s_rc_last`的正常产出节奏，属于测试环境本身引入的次生问题，不是SD卡问题的一部分，也不是`g_imu_health.dual_fault`/`g_power_health.voltage_fault`误触发（两者确认均为0）。
5. 为彻底排除其他Task/ARM状态机/RC/IWDG的干扰，新增独立测试文件`App/Src/app_sdtest_demo.c`（`App_SdTest_Task`），绕开ARM/RC/黑匣子懒加载/FatFS，直接调用`BSP_SD_Init`+多轮`BSP_SD_WriteBlock`裸测。测试时只保留这一个Task运行，其余全部关闭（含`Task_IWDG_Feed`，同时确认`main.c`里`MX_IWDG_Init()`本身也需要注释掉，否则会在约512ms后被意外复位——`DBG_IWDG_STOP`寄存器位仅在调试器真正Halt状态下才冻结IWDG计数，"点Run观察"这种操作模式下大部分时间CPU是自由运行的，不受这个位保护，此前一度误以为IWDG不会是问题，被这次实际现象纠正）。
6. 干净环境下测试结果：`g_sdtest_result[]`5轮全部约10.1~10.27秒，`g_sdtest_write_result[]`全部是`-2`（失败，不是成功）。这纠正了此前"约10秒卡顿后成功完成"这个持续了很久的描述性错误——回查代码发现`SD_DMA_TIMEOUT_MS`当前仍是调试期间临时调大的5000ms，5秒软件超时后`SD_SPI_DMA_Transceive`返回`-3`，被`BSP_SD_WriteBlock`统一包装成对外的`-2`，从未有一次真正走到CRC/Data Response/Busy等待这些后续步骤，更没有真正成功过。
7. 在`HAL_SPI_TxRxCpltCallback`里插入PB9 GPIO翻转（确认测试环境下`Task_Indicator`未运行，不会与`app_indicator.c`报警节拍冲突，可以安全复用这颗LED做诊断），逻辑分析仪同时抓CS/SCK/PB9三线，精确验证：完成回调确实是在SCK活跃窗口结束的那一刻（约5.1秒处）就触发的，不是等满后面的静默期才触发——这解开了"完成回调什么时候真正触发"这个悬念，但也带来新的推论：`g_sdDmaLastElapseMs`此前记录的"约10.4秒"很可能是"上一次已经放弃等待的传输，姗姗来迟触发的完成信号，撞上了当前正在测量的这一轮"，测量本身可能存在跨越两次调用的污染，此前"传输耗时10.4秒"的说法需要打问号。
8. 在`SD_SPI_DMA_Transceive`函数内`HAL_SPI_TransmitReceive_DMA`调用成功返回后设置精确断点（确保命中时刻DMA刚被成功发起），单点采样：`DMA1_Stream3->CR`（RX）EN=1、NDTR会正常递减到0；`DMA1_Stream4->CR`（TX）EN=0、NDTR全程保持512不变；`SPI2->CR2=0x23`（RXDMAEN/TXDMAEN均已使能，配置无误）；`DMA1->HISR`全程为0（无错误标志）；静默期读`SPI2->SR=0x02`（TXE=1、BSY=0，SPI外设本身空闲，不是被卡住）。
9. **未解开的矛盾**：TX方向（Stream4）寄存器读数显示"从未启用过"（EN=0且NDTR从未偏离初始值512），但RX方向确实收到了数据、SCK确实有活动——物理上，SPI全双工的RX数据必须由TX驱动SCK才能产生，两者不可能一个在跑一个完全没跑。排查在这里因精力原因中止，达成一致：下一步必须用逻辑分析仪**同时**（不是分开单独接）抓CS+SCK+MOSI+MISO四线，重点看活跃窗口内MOSI和MISO是否逐字节同步，这是纯软件调试手段已经无法回答的问题（记录八用这个矛盾为线索，最终定位到CCM RAM根因，见下文）。

**教训/方法论总结**：

- **断点暂停会让程序中断整个CPU核心的执行**，不只是暂停被调试的那个RTOS任务——早期怀疑Live Watch问题、后期怀疑寄存器采样问题，多次因为忘记这一点走了弯路。
- **调试器的Halt对硬件外设行为的暂停范围是有限的**：DMA传输和IWDG计数都不会因为CPU被Halt在某一行代码而必然暂停——DMA是独立硬件时序，不受CPU暂停影响（这一点后来被反过来利用，用来验证NDTR的真实变化）；IWDG则只在调试器真正把CPU置于Halt状态时才受`DBG_IWDG_STOP`保护，"自由运行、隔几秒手动暂停一次"这种操作模式下的大部分时间里其实完全不受保护，是这次排查里一个反复被搞混、最后才理清楚的点。
- **外层函数会吞掉内层的具体错误码**：`BSP_SD_WriteBlock`把`SD_SPI_DMA_Transceive`内部所有的失败原因（真正发起失败/等待超时/DMA错误标志）统一包装成外层自己的单一错误码`-2`对外返回，调试时如果只看外层返回值容易对失败原因产生误判，必须回到调用链更内层去看真正的返回路径。
- **精确断点优于自由运行+手动Halt**：早期多次尝试用"自由运行、隔几秒手动暂停看一眼寄存器"的方式采样，多次出现自相矛盾的结果（比如同一个寄存器不同次读数逻辑上对不上），后来改用"固定在某一行必然发生的代码位置设断点"的方式，结果的可信度明显更高、更容易复现验证。即便如此，这次仍然遇到了单点断点采样也无法解释的矛盾（TX/RX寄存器读数矛盾），说明面对微秒级的DMA时序问题，纯软件调试手段存在天花板，逻辑分析仪这类独立于CPU时序的硬件工具是不可替代的。
- **简化测试环境时，要考虑被裁剪部分和保留部分之间的隐藏依赖**：为了排查SD卡DMA问题而临时精简`Task_FlightCtrl`循环体时，一度只想着"去掉重运算、保留Arm_Update"，忽略了`Arm_Update`依赖的输入（姿态角、RC数据）本身也来自被裁掉的那部分代码，导致引入了一个全新的、与原问题无关的次生现象（ARM反复横跳），一度污染了测量数据、浪费了排查精力。

### 波形复测（受限于逻辑分析仪只有两通道，分两轮抓取）

- 无法真正同时抓CS+SCK+MOSI+MISO四线，改为同一个`App_SdTest_Task`测试环境下连续两轮触发：第一轮抓CS+SCK，第二轮抓MOSI+MISO，靠活跃窗口时长高度吻合做对齐推断。
- CS+SCK这一轮实测：单次活跃窗口约5.1~5.15秒，内部由大量以约10ms为间隔的小区间构成，每个小区间内部是约2.5MHz的真实SPI时钟；一次完整的CS周期（含静默期）约10.2~10.35秒；活跃窗口内帧头2字节、帧尾约39字节间隔约3μs（正常速度），中间大段字节间隔约10ms（异常）。
- **关键数字巧合**：5.12s ÷ 10ms ≈ 512，精确对应SD Block大小（512字节），不是巧合——这个活跃窗口本质上是某种机制在以"每字节间隔约10ms"的节奏逐字节推进这512字节，而不是硬件本身跑不动。
- MOSI+MISO这一轮实测（人工测量，可能有波动）：MOSI在帧头发送几个固定的短脉冲后，中间以约10ms为间隔陆续发出若干组短脉冲，MISO在同一时间窗口内也呈现类似节奏、但夹杂长时间的高/低电平保持段。两轮波形的活跃周期都约5秒，整体周期都约10秒，与CS+SCK那一轮吻合。

### HAL库源码核对

- 核实ST官方`stm32f4xx_hal_spi.c`里`HAL_SPI_TransmitReceive_DMA`的真实实现，确认两个关键事实：
  1. **RX方向的DMA（`hdmarx`）先于TX方向（`hdmatx`）被`HAL_DMA_Start_IT`启动**
  2. **TX方向的DMA错误回调被显式置空**（`hspi->hdmatx->XferErrorCallback = NULL;`），意味着如果TX DMA触发Transfer Error，不会有任何TX专属的软件回调被调用，但`HAL_DMA_IRQHandler`本身仍会按流程处理、清标志位、把对应Stream的`EN`位清掉——这一步不依赖回调是否为空
- 这两点后续被证明是解释寄存器现象（TX Stream4读数EN=0/NDTR不变、`DMA1->HISR`事后读出来是0）的关键。

### 复查外设配置与中断绑定

- 复查`spi.c`（CubeMX生成）：SPI2的DMA配置（Stream/Channel映射、`DMA_PRIORITY_VERY_HIGH`、FIFO模式）本身核对无误。附带发现CubeMX默认给的`BaudRatePrescaler`是`_128`档，不是设计值÷16，但这个初始值只在握手阶段（阻塞式单字节收发）生效，`BSP_SD_SetSpeedFast()`会在握手完成后覆盖成÷16，不影响DMA传输这个环节，只是记录不作为问题处理。
- 复查`dma.c`：`DMA1_Stream3`/`Stream4`NVIC优先级均为8，在`configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY=5`安全范围内，跟其余Stream（2/5/6，DMA2 Stream5）对照无异常。
- 复查`stm32f4xx_it.c`：`DMA1_Stream3_IRQHandler`绑定`hdma_spi2_rx`、`DMA1_Stream4_IRQHandler`绑定`hdma_spi2_tx`，绑定正确无误。
- **顺带发现的独立问题**：`SPI2_IRQn`从未在NVIC使能过（`dma.c`没有对应的`HAL_NVIC_EnableIRQ`调用，`stm32f4xx_it.c`也没有`SPI2_IRQHandler`实现）。`HAL_SPI_TransmitReceive_DMA`内部会使能SPI错误中断位（`SPI_IT_ERR`），这个中断走的是`SPI2_IRQn`这条独立的线，不是DMA Stream中断。经核实这次问题期间`SPI2->SR`全程无错误标志，这个缺口本次没有被触发、不是根因，但标记为待补的健壮性缺口。

### 核心突破：链接map文件核对

- 核对链接生成的`CubeMX_Create.map`符号表，发现`bsp_sdcard.c`里DMA全双工传输实际使用的两个512字节scratch buffer：
  - `s_sdTxDummy`（`BSP_SD_ReadBlock`的TX方向填充源）地址落在`0x100001f0`
  - `s_sdRxSink`（`BSP_SD_WriteBlock`的RX方向丢弃桶）地址落在`0x100003f0`
  两者都落在`0x10000000~0x1000FFFF`这个地址范围内——这正是STM32F405的CCM data RAM。
- 顺藤摸瓜复查同一份map里的其他DMA相关buffer：`bsp_dshot.c`的DSHOT输出buffer`s_dshot_buf`（走`DMA2_Stream5`/`hdma_tim1_up`做TIM1 burst DMA）同样落在CCM（`0x10000160`）；`bsp_elrs.c`的`s_dma_rx_buf`（USART2 DMA接收）、`bsp_gps.c`的`gps_dma_buf`（UART4 DMA接收）、`bsp_blackbox.c`的`s_buf`（黑匣子双缓冲）均落在正常的SRAM1区间（`0x20000000`起），是安全的。

### 根因确认

参考RM0090《Reference manual》第2章"Memory and bus architecture"，2.1节"System architecture"（Figure 1系统架构图）及2.3.1节"Embedded SRAM"：STM32F405拥有两块物理独立的SRAM——一块112KB挂在AHB Bus matrix-S上（地址`0x20000000`起，SRAM1），所有Bus Master（CPU、DMA1、DMA2、以太网DMA等）都能通过总线矩阵访问；另一块64KB是CCM data RAM（地址`0x10000000`起），**直接点对点连接到Cortex-M4内核的D-bus，完全不接入Bus matrix-S**。系统架构图上，CCM data RAM根本不是矩阵网格里的一个节点，DMA1/DMA2引出的`DMA_MEM1`/`DMA_MEM2`两条访存路径在矩阵里也没有任何连接能到达CCM。

据此确认：**任何Bus Master（包括DMA1、DMA2）在物理拓扑上都无法访问CCM，这是芯片设计层面的硬限制，不是配置错误**。DMA尝试对CCM发起传输时，不表现为"访问被拒绝、立刻报错"这种干净的失败，而更接近"总线请求得不到任何从设备响应、DMA状态机停滞"，最终由软件层面的5秒超时兜底返回——这与TX Stream4读数"EN=0、NDTR全程不变"（未能真正建立起有效传输）、以及`DMA1->HISR`事后读出为0（HAL处理流程清空了标志位，配合TX错误回调被置空，不产生额外的软件层报错）的实测现象完全吻合。

### 定位链接器打包不可控的原因

- 复查工程的`CubeMX_Create.sct`：`RW_IRAM1`（SRAM，`0x20000000`起）和`RW_IRAM2`（CCM，`0x10000000`起）两个execution region均使用`.ANY(+RW +ZI)`不加区分地接收任意普通变量，链接器按内部打包算法自由分配，完全不理解"这个变量以后会被DMA外设读写"这层C代码语义。
- 这解释了为什么问题会在不同编译版本之间"跳来跳去"：最初一份独立测试代码（`app_sdtest_demo.c`）里的测试buffer落进CCM，删除该测试文件重新编译后，落进CCM的变成了`bsp_sdcard.c`的两个正式buffer——工程里增删任意一个源文件，都会让链接器的打包结果重新洗牌，这是一类系统性问题，不是某个变量"运气不好"。

### 修复方案

1. **`.sct`收紧CCM的准入条件**：`RW_IRAM2`（CCM）不再接受`.ANY`，只接受显式标记的`*(DMA_UNSAFE_CCM)`段（目前工程里没有任何变量使用这个标签，CCM保持为空，链接时会有一条"没有匹配段"的`L6314W`警告，属预期行为）；`RW_IRAM1`（SRAM）在原有`.ANY(+RW+ZI)`基础上，额外显式接收`*(DMA_SAFE_SRAM)`段。
2. **源码层面显式标记DMA安全buffer**：`bsp_sdcard.c`的`s_sdTxDummy`/`s_sdRxSink`、`bsp_dshot.c`的`s_dshot_buf`，用armcc的`#pragma arm section zidata="DMA_SAFE_SRAM"` … `#pragma arm section zidata`包裹，强制链接到SRAM，不依赖链接器的默认打包行为。
3. **关闭Keil的Scatter File自动生成**：Keil默认会在每次编译时根据"Options for Target → Linker → Use Memory Layout from Target Dialog"这个设置，按Target页签的IROM/IRAM配置自动重新生成`.sct`、覆盖手改内容。取消勾选这个选项、显式指定Scatter File路径指向手改后的`CubeMX_Create.sct`，改动才能在每次Rebuild后持续生效。

### 验证

- Rebuild All后核对`CubeMX_Create.map`，三个符号地址分别变为`0x2000dc8c`（`s_dshot_buf`）、`0x2000de9c`（`s_sdTxDummy`）、`0x2000e09c`（`s_sdRxSink`），Section标记为`DMA_SAFE_SRAM`，全部落在SRAM1（`0x20000000~0x2001FFFF`）区间内，确认是被`#pragma`精确摆放，不是碰运气落对的。
- 烧录上机后重新测试`BSP_SD_WriteBlock`，DMA全双工传输不再超时，黑匣子成功建立并写入日志文件（`LOG000.BIN`/`LOG001.BIN`）。

### 副作用：SD卡内遗留损坏文件

- 排查期间反复的异常复位/未正常关闭文件，导致SD卡FAT目录区残留几条损坏的目录项（文件名乱码、大小异常接近4GB、Windows资源管理器无法正常删除）。用SD Association官方SD Card Formatter工具做完整格式化解决——Windows自带的快速格式化不够彻底，不建议用来处理这类目录区损坏的场景。

### 教训

- **CCM RAM"能不能被DMA访问"是芯片物理拓扑层面的硬限制，C编译器和链接器都无法自动规避**，必须靠scatter文件的显式分区设计（或`#pragma`标记）主动告知链接器哪些变量不能落进CCM。
- **链接器对未加区分的多个RW/ZI候选region的打包结果本质上不可预测，且会随工程文件增删重新洗牌**——不能靠"这次跑起来正常"判断一个变量的最终落点是安全的，必须实际去map文件核对地址，尤其是任何会被DMA/其他总线Master访问的buffer。
- 记录六、七排查的方向（NVIC优先级、DMA中断绑定、SPI时钟配置、信号量污染、超时后DMAStop等）全部属于"配置正确性"层面的检查，而这次的根因属于"内存物理拓扑"层面，是完全不同的维度——排查陷入僵局、所有"配置层面"的可能性都验证过一遍仍然无解时，需要考虑跳出"配置对不对"这个框架，往更底层的"这块内存这个Bus Master到底够不够得着"这类硬件拓扑问题上查。
- 关闭Keil的Scatter File自动生成这一步容易被忽略——手改`.sct`之后如果不做这一步，下一次编译又会被自动生成的版本覆盖回去，改了等于白改。
