## 二、RTOS架构

**8个业务Task + 1个看门狗Task**：`Task_FlightCtrl`（osPriorityRealtime7）、`Task_RC_Link`、`Task_Nav`、`Task_Blackbox`、`Task_Telemetry`、`Task_PowerMonit`、`Task_Indicator`、`Task_IwdgFeed`

> 无`Task_IMU2_RDD`——双IMU冗余判定是`Task_FlightCtrl`内部直接调用`ImuRedundancy_Update()`，不拆独立Task（拆出去会引入不必要的任务切换延迟，抵消实时性收益）。同理，ARM状态机（`app_arm.c`）也不单开Task，跟`Task_FlightCtrl`同级，作为模块被每循环调用。

> ⚠️**`app_arm.c`里有一个调试专用宏`DEBUG_SKIP_ARM_READY_CHECK`，当前为`1`**（跳过`SystemReadyEventGroup`前置检查，方便在GPS/MAG/RC没接通的情况下单独测ARM状态机本身）。装机带桨试飞前**必须**改回`0`或删除这段`#if`，否则解锁条件形同虚设。`grep DEBUG_SKIP_ARM_READY_CHECK`能定位到全部相关代码。

> `Task_Blackbox`现在是**懒加载**：开机不自动挂载SD卡/建文件，纯阻塞等第一次`BB_RequestNewFile()`（即第一次真正解锁）才触发`BB_Init()`；`Armed→Disarmed`时关闭当前文件，回到"没有文件"状态，等下一次解锁再开新文件。每次飞行对应一份独立日志，不会在地面静置期间凭空建空文件。

**Queue/Mailbox**：

- `RCChannelMailbox`（深度1+覆盖式写入，`RCChannelData_t`，类型定义归属`bsp_elrs.h`）
- `NavStateMailbox`（深度1+覆盖式写入，`NavState_t`）
- `MagDataMailbox`（深度1+覆盖式写入，`MagData_t`）
- `IndicatorEventQueue`（深度8，`IndicatorEvent_t`）
- `NavCommandQueue`（深度4，`NavCommand_t`）

覆盖式写入统一按`osMessageQueueGetSpace`查满→满了先`Get`丢弃旧值→再`Put`实现（CMSIS-RTOS2无原生`xQueueOverwrite`）。

> 黑匣子不再走Queue——`Task_Blackbox`改为双缓冲+信号量驱动，详见"十一、黑匣子"。

**Event**：`SystemReadyEventGroup`，五个bit，ARM解锁前必须全部置位，**已全部接线完成**：

```c
SYSREADY_BIT_HOME_VALID      // Task_Nav置位：s_home_valid同步
SYSREADY_BIT_MAG_OK          // Task_Nav置位：I2C读取成功 && !OVFL
SYSREADY_BIT_VOLTAGE_OK      // Task_PowerMonit置位：见"八、电源监控"
SYSREADY_BIT_RC_LINK_OK      // Task_RC_Link置位：直接复用bsp_elrs.c的link_ok
SYSREADY_BIT_IMU_HEALTH_OK   // Task_FlightCtrl置位：镜像!g_imu_health.dual_fault，每循环更新
```

> `IMU_HEALTH_OK`这个bit只在`Arm_Update`的Disarmed分支（解锁前置条件）被检查，Armed期间不重复检查——单IMU故障切换（冗余机制正常工作）不会置`dual_fault`，不影响继续飞行；两路都坏时`dual_fault`置位走的是Armed分支里独立的紧急disarm检查，不依赖这个bit。

**Mutex/Semaphore**：总线/外设访问不需要——每条总线/外设都被唯一Task独占访问。`Task_Blackbox`的双缓冲用信号量做消费者同步。

**IWDG**：512ms超时（4095 reload, 4 prescaler）。喂狗权限只属于`Task_IwdgFeed`，其余Task只上报心跳时间戳到`g_heartbeat`，不直接调`HAL_IWDG_Refresh`。⚠️**`DBG_IWDG_STOP`只在CPU真正处于调试器暂停(Halt)状态时才冻结IWDG计数，自由运行(Run)期间完全不受这个位保护**——如果做隔离测试时连`Task_IwdgFeed`一起关掉了，必须连`main.c`里的`MX_IWDG_Init()`调用本身也一起注释掉，否则会在约512ms后被意外复位，且现象容易被误判为"程序莫名跳回开头重新执行"。**当前`main.c`里`MX_IWDG_Init()`已被注释（调试状态，装机前需要恢复）。**

**FreeRTOS关键配置**：

- `configUSE_PREEMPTION = 1`（抢占式调度，已确认）
- `configTIMER_TASK_PRIORITY = 55`（跟`Task_FlightCtrl`打平，官方推荐Timer Task用最高优先级）
- `LIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY = 5`；EXTI4=6，EXTI15_10=5（不对称但都在安全范围内）
- `TICK_RATE_HZ = 1000`
- `TOTAL_HEAP_SIZE = 49152 Bytes`
- HAL Timebase用TIM6（不用SysTick，避免FreeRTOS接管SysTick后`HAL_GetTick`卡死）
- `DBG_IWDG_STOP`：CubeMX GUI里找不到对应勾选项，已在`IWDG_Init`里手动加`#if defined(DBGMCU_APB1_FZ_DBG_IWDG_STOP) DBGMCU->APB1FZ |= DBGMCU_APB1_FZ_DBG_IWDG_STOP #endif`（条件编译保护不同芯片型号；注意这个保护仅在调试器Halt状态下生效，见上方IWDG小节说明）

## 三、分层与命名约定

- **alg层**（`alg_pid`/`alg_controller`/`alg_mixer`/`alg_attitude`）：纯数学，不碰HAL、不碰RTOS对象、不知道数据来自哪颗传感器。函数参数命名按物理意义取（如`roll_rate`而非`gx`），不暴露硬件相关命名。
- **bsp层**（`bsp_icm42688`/`bsp_qmc5883`/`bsp_gps`/`bsp_elrs`/`bsp_dshot`/`bsp_power`/`bsp_blackbox`/`bsp_sdcard`/`bsp_led`/`bsp_buzzer`）：内部`static`存最新数据，对外只暴露`XXX_CopyTo(&out)`或纯执行接口（如`bsp_dshot`不做判断，只按传入值编码发送）。传感器坐标系/贴装朝向的hack在这一层内部消化，不上抛。**该数据类型的定义归属生产它的bsp模块的头文件**（`IcmData_t`在`bsp_icm42688.h`，`MagData_t`在`bsp_qmc5883.h`，`RCChannelData_t`在`bsp_elrs.h`），不要放`app_shared_types.h`。
- **app层**（`app_flightctrl`/`app_nav`/`app_rc_link`/`app_arm`/`app_power_monitor`/`app_iwdg_feed`/`app_blackbox`/`app_indicator`）：任务编排、状态机、跨Task共享状态的实际存储。
- **`app_shared_types.h`只放两类东西**：(1) 没有唯一生产者、由某Task组装多来源拼出来的类型（如`NavState_t`）；(2) 真正跨Task共享的状态本体（`g_imu_health`、`g_heartbeat`、`g_power_health`、`g_arm_state`）。不是"只要跨模块用就往这塞"。
- **模块内部私有的辅助结构体不进头文件**（如`bsp_qmc5883.c`内部的`MAG_Data_t`原始值容器、`bsp_blackbox.c`内部的帧结构体，只在`.c`里`static`，不暴露）。
- **结构体传参不做强制类型转换，逐字段拷贝**——曾在`MagData_t`/`MAG_Data_t`混用踩过坑。
- Task内部延时用`osDelay`，不用`HAL_Delay`（阻塞式破坏调度）；`HAL_Delay`仅限调度器启动前使用。
- HAL弱函数回调（`HAL_GPIO_EXTI_Callback`、`HAL_UARTEx_RxEventCallback`）全工程仅一份实现，走专门dispatch文件按Pin/Instance分流。
- `freertos.c`里`StartTask_XXX`函数体只做一行转发调用（`App_XXX_Task(NULL)`），业务逻辑不写在这里；转发用`#include "app_xxx.h"`而非手写`extern`。
- **单字节/单枚举的跨Task共享状态**（如`g_arm_state`）走`extern volatile`直接读，不用CopyTo——撕裂读风险可忽略；体积较大的结构体（如`fc`）才用CopyTo。

## 四、双IMU冗余（`app_imu2_redundancy.c`）

- ODR统一800Hz（ACC/GYRO），寄存器配置见下表。

| 寄存器 | 地址 | 值 | 含义 |
| --- | --- | --- | --- |
| ACC_RANGE | 0x41 | 0x03 | ±16G |
| ACC_CONF | 0x40 | 0x8B | 高性能, BWP=000, ODR=800Hz |
| GYR_RANGE | 0x43 | 0x00 | ±2000dps |
| GYR_CONF | 0x42 | 0xCB | 高性能+噪声优化, BWP=00, ODR=800Hz |
| INT_CFG1 | 0x06 | 0x03 | 推挽输出, 高有效, DRDY_GYR |
| PWR_CTRL | 0x7D | 0x0E | TEMP+ACC+GYR全开 |

- `ICM_InitAll()`里对两颗IMU都强制发起一次`ICM_ClearDataReadyLatch()`（**必须是完整13字节burst读**，只读1字节无法真正清除锁存，曾因长度参数误写为2导致锁存复发），打破"上电即锁存死锁"（芯片INT1是固定电平锁存型，写`INT_CFG1`生效瞬间若DRDY状态位已是1会直接锁死，EXTI永远等不到上升沿）。
- `App_FlightCtrl_Task`在`ICM_InitAll()`之后、进入主循环`for(;;)`之前**不得**对`g_icmDataReadyEvtId`做额外的`osEventFlagsClear`——`osEventFlagsNew()`创建的事件对象本身默认清零，多余的显式清除只会在初始化函数耗时恰好跨过第一次真实DRDY窗口（~1.25ms）时，把这次真实事件误吞掉，导致永久死锁（曾踩过这个坑，详见《变更与踩坑记录》记录五插曲）。
- `Task_FlightCtrl`用`osEventFlagsWait(..., osFlagsWaitAny, 4ms超时)`等待任一IMU的DRDY。交叉比对、staleness检查**无条件每次循环执行**（不依赖两路DRDY同时到达，`osFlagsWaitAny`几乎不可能同时捕获两路独立时钟）。
- Staleness检查：`MAX_AGE_S = 3.0f / 800`，任一IMU数据龄期超过此值判定异常（防止"数据被冻结但数值巧合对得上"的盲区）。
- 六轴交叉比对阈值分开判断，取静止批稳健统计（median+4×MAD）与动态批P99的较大值：

```c
ACC_AX_DIFF_THRESHOLD_G    = 0.1005f
ACC_AY_DIFF_THRESHOLD_G    = 0.0244f
ACC_AZ_DIFF_THRESHOLD_G    = 0.0898f
GYRO_GX_DIFF_THRESHOLD_DPS = 1.9520f
GYRO_GY_DIFF_THRESHOLD_DPS = 2.5620f
GYRO_GZ_DIFF_THRESHOLD_DPS = 3.5990f
```

  **⚠️这批阈值仍是PROVISIONAL**——采集窗口跨越了IMU2从故障到修复的调试过程，尚未用完全修复的链路重新测过静止批+动态批。静止批采集已重新开始，动态批需装机后补测。

- 切换策略（快切慢回）：连续5帧异常判定切走（`SWITCH_AWAY_THRESHOLD`），连续200帧健康判定切回（`SWITCH_BACK_THRESHOLD`）。
- **备用IMU的健康标志可以恢复，但不主动切回**——两颗物理对等，没有理由为切换而切换；只有当前active的一路自己触发`Health_RecordBad`时才检查备用是否可用。
- **双路失效处理**：`Health_RecordBad`触发切换前会先检查备用是否健康，不健康则冻结`active_imu_sel`不变，置起`g_imu_health.dual_fault`锁存标志，数据仍输出但下游需自行判断是否信任。`dual_fault`在`Health_RecordGood`里、当前active路持续正常时解除。**下游动作**：`dual_fault`置位时，`Arm_Update`会阻止解锁（Disarmed分支）或立即disarm（Armed分支），见"六、ARM状态机"。
- 零偏补偿：切换瞬间不做offset淡出，接受可能的小抖动。
- 姿态融合状态（`Attitude_t`）在IMU切换时**保留、不重置**——两颗IMU物理朝向一致，切换只是数据来源换了。
- dt用`DWT->CYCCNT`实测，钳位±20%标称值兜底（防止调度异常帧污染PID）。

## 五、姿态融合与控制链

**分工**：`bsp_icm42688.c`在读取时完成ax/ay、gx/gy换轴（贴合IMU贴装朝向对齐NED），`alg_attitude.c`拿到的输入已经是这个约定下的坐标系，内部不再做任何朝向修正。

**pitch轴取负、roll轴不取负**这条规律，只在两处调用点生效，不进`alg_attitude`：

```c
AngleController_Update(fc.roll_target, fc.pitch_target, fc.roll_meas, -fc.pitch_meas, dt);
RateController_Update(..., active_data.gx, -active_data.gy, active_data.gz, dt);
```

`fc.pitch_meas`本身（黑匣子记录用的值）不取负，取负只发生在喂给控制器比较目标的那一刻。`Map_Pitch`已确认沿用旧代码"前推=低头、后推=抬头"这套映射，符号不需要额外处理，问题关闭。

**遥控通道映射**（`alg_controller.c`）：

```c
Map_Roll(ch)  = (ch - 991.5f) / 819.5f * 30.0f   // ±30°
Map_Pitch(ch) = (ch - 991.5f) / 819.5f * 30.0f   // ±30°
Map_Yaw(ch)   = (ch - 991.5f) / 819.5f * 90.0f   // ±90°/s
```

角度上限从±20°上调到±30°——这是遥控能要求到的目标角权限上限，跟PID调参是独立的两件事：户外10寸机型风扰下，实际姿态角容易触及±20°上限，压杆到顶也无法要求更大纠偏角度；上调后留出更多抗风裕量，同时离60°倾角保护还留足安全边际。

**控制链路顺序**（`Task_FlightCtrl`循环，800Hz）：

```
ImuRedundancy_Update → 更新SYSREADY_BIT_IMU_HEALTH_OK
→ Attitude_ComputeAccelAngles/Attitude_Update
→（非阻塞取MagDataMailbox命中则）Attitude_CptYaw
→（非阻塞取RCChannelMailbox，未命中沿用上次值）
→ Arm_Update（ARM状态机，见"六"）
→ FlightControl_Update（RC映射+Yaw模式切换+角度环+角速度环+动态限幅）
→ Mixer → m1~m4
→ 按g_arm_state分支：Armed发BSP_DSHOT_Send(m1~m4+48)，否则发BSP_DSHOT_Send(0,0,0,0)
```

**Yaw控制**：手动模式（channel[5]>1500）直接`Map_Yaw`映射角速度目标，摇杆量小于5°/s视为0；否则Heading Hold模式，`YawHeadingHold_Update`用PID闭环锁定航向，模式切入瞬间锁定当前航向并清零积分。

**动态限幅**：`fc.throttle < 30`时持续调用`FlightControl_Reset()`（复位所有控制器和积分项，防止地面怠速积分饱和）；油门起来后，姿态修正量允许幅度按`fc.throttle - 30`动态放宽，上限250。

**RTH（自动返航）当前不接入**——旧代码本身标注"未经实机测试，严禁开启"，`Task_Nav`目前也不产出RTH所需的bearing/dist，等真正要做返航再补这条分支。

## 六、ARM状态机（`app_arm.c`）

跟`Task_FlightCtrl`同级、不单开Task（所需RC数据/倾角数据均已在该循环中现成可用，拆出去只会引入信箱抢占问题，没有收益），文件是模块，由`Task_FlightCtrl`每循环调用`Arm_Update()`。状态`extern volatile ArmState_t g_arm_state`直接读，不用CopyTo。

**通道索引确认无误**：`ARM_RC_CHANNEL_SWITCH=4`对应遥控器CH5（人类习惯编号从1起，数组从0起，CH5=SD=channels[4]），`ARM_RC_CHANNEL_THROTTLE=2`对应CH3=THR，两者索引均已核对确认正确，不是bug。

**状态转移**：

```
Disarmed ──(RC ARM键 + 低油门 + 倾角<30° + SystemReadyEventGroup全部就绪)──▶ Armed
Armed ──(RC DISARM键 + 低油门，持续满6秒)──▶ Disarmed        （正常落地）
Armed ──(dual_fault / voltage_fault / 倾角保护触发，立即)──▶ Disarmed  （紧急disarm）
```

- **两个30°的检查不是同一件事**：`Arm_TiltOk`（解锁前置条件）判定的是"起飞前地面是否水平"；飞行中的`TiltProtection_Check`用的是独立的**60°**阈值，判定"是否已经失控/翻转"。两者物理意义不同，不能共用同一个常量——正常飞行中的机动/抗风纠偏会自然超过30°，但不该被当成失控。60°是经验取值：留出约一倍于正常机动的余量，同时离90°（基本等于已经翻了）还留足反应空间。
- **正常落地disarm的6秒debounce**用时间戳判断（条件首次满足时记录`osKernelGetTickCount()`，之后每帧比对差值，条件中断则清零重来），不是轮询计数式的debounce。
- **紧急disarm三条判据（`dual_fault`/`voltage_fault`/倾角保护）立即触发，不走debounce**——这三者代表持续性故障或已失控，跟"正常收桨"不是一回事，堵转的代价远小于迟疑一拍。
- Disarmed时`dual_fault`或`voltage_fault`置位会直接禁止解锁（倾角判据依赖IMU数据，数据不可信则无法验证解锁前提）。
- ⚠️**如果`Task_FlightCtrl`循环体被简化/裁剪用于调试（比如只保留`Arm_Update`调用、去掉姿态解算/RC正常轮询节奏），务必注意`Arm_Update`依赖的`roll_meas`/`pitch_meas`/`s_rc_last`这些输入如果失去了正常的产出节奏，ARM状态可能会在Armed/Disarmed之间反复横跳（进而连带触发`BB_RequestNewFile`/`BB_RequestClose`反复调用、蜂鸣器反复报警）。这不代表状态机本身有bug，是测试环境破坏了它依赖的输入完整性导致的次生现象。**

## 七、DSHOT输出（`bsp_dshot.c`）

纯执行层：不做ARM判断、不做量程二次映射，`BSP_DSHOT_Send(p1,p2,p3,p4)`四个入参直接当DSHOT 11-bit payload编码发送。是否解锁、要不要加48偏移，由调用方（`Task_FlightCtrl`读`g_arm_state`）决定后传入成品值：

```c
Armed    → BSP_DSHOT_Send(m1+48, m2+48, m3+48, m4+48)   // m1~m4即Mixer输出，0~1352
Disarmed → BSP_DSHOT_Send(0, 0, 0, 0)                     // 持续发送纯0，不是停止调用
```

Disarmed状态**必须持续调用发送纯0帧**，不能"不解锁就不调用发送函数"——长时间收不到DSHOT帧流可能触发电调自身的失控保护/报警。

`Mixer`输出上限`MIXER_OUTPUT_LIMIT = 1352`（不是DSHOT满量程2047），是电流保护的刻意选择，针对当前4in1 65A电调板与实际负载（见"一、硬件与引脚"）留出的裕量；`bsp_dshot`层不对这个上限做拉伸映射。

DMA burst缓冲区元素类型是`uint16_t`（跟`hdma_tim1_up.Init.MemDataAlignment=DMA_MDATAALIGN_HALFWORD`绑定，不能因为`HAL_TIM_DMABurst_MultiWriteStart`函数原型接收`uint32_t*`就改成`uint32_t`，否则发出去的数据会错位）。`BSP_DSHOT_Init()`里补了`HAL_TIM_PWM_Start`四通道调用——`MX_TIM1_Init`本身没有真正启动PWM输出这一步。

`s_dshot_buf`（DMA burst源缓冲区）通过`#pragma arm section zidata="DMA_SAFE_SRAM"`显式标记，确保链接到SRAM而非CCM，见"十五、内存布局与DMA安全"。

## 八、电源监控（`bsp_power.c` + `app_power_monitor.c`）

`Task_PowerMonit`独立FreeRTOS Task，100ms周期。ADC1 Scan两通道触发一次转换（**软件触发，不使用DMA**），VBAT/电流一起读出（`BSP_Power_Read`），当前电流值只读出存着、不参与任何判断——过流保护阈值需要真实台架测试数据支撑，不能凭旧代码经验值（针对不同机架/电调配置）照搬，留待专门测试。

**VBAT判据**：

```c
VBAT_DISARM_THRESHOLD  = 13.2f   // 4S电池单片3.3V下限，换电池节数改这一处
VBAT_RECOVER_THRESHOLD = 13.5f   // 迟滞：回升到此值以上才重新置VOLTAGE_OK
VBAT_FAULT_CONFIRM_COUNT = 5     // 连续5次(~500ms@100ms周期)低于阈值才确认voltage_fault
```

连续确认+迟滞，是为了滤掉大机动瞬时压降造成的误判、防止临界点抖动反复置/清`VOLTAGE_OK`。`g_power_health.voltage_fault`置位后，供`Arm_Update`做紧急disarm判据。

## 九、ELRS/RC链路 —— ✅此前"数据自由运行时冻结"问题已解决

- `bsp_elrs.c`：USART2 DMA循环接收，`ELRS_Poll`追赶DMA读写指针喂状态机组帧，CRC8校验通过后解析0x16（通道）/0x14（链路质量）帧。
- CRC8校验范围是`frame_buf[2]`到`frame_buf[frame_len-2]`（Type+Payload，不含Sync/Len），循环从`i=2`开始。
- 失联判定：`CRSF_FAILSAFE_TIMEOUT_MS = 70`（150Hz标称间隔6.67ms×10倍留裕量，**未做真实断链测试验证，数值待校准**）。
- `Task_RC_Link`轮询周期4ms（150Hz下留约3倍余量，DMA_BUF_SIZE=128字节可扛约2帧）。
- `ELRS_CopyTo`输出类型是`RCChannelData_t`（定义在`bsp_elrs.h`），跟`app_shared_types.h`里其他类型统一大小写风格，不要出现`RcChannelData_t`这种大小写变体。
- `RC_LINK_OK`这个EventGroup bit直接复用`bsp_elrs.c`已算好的`link_ok`字段，`Task_RC_Link`每循环同步置位/清位，已接入。

**✅根因与修复（已解决）**：`usart.c`里`hdma_usart2_rx`的DMA Mode曾配置为`DMA_NORMAL`，收满128字节`DMA_BUF_SIZE`后DMA自动停止、不重载，导致USART2 DMA只接收一轮数据后彻底停止接收（`__HAL_DMA_GET_COUNTER`读出的`counter`卡死在0，不再变化），`s_rc_data`此后永久冻结在最后一次成功解析的快照上。已在CubeMX里将`USART2_RX`对应DMA Stream的Mode改为`DMA_CIRCULAR`，重新生成代码后验证修复有效，数据能持续正常刷新。

## 十、GPS/导航（`app_nav.c`）

- `Task_Nav`周期20ms，负责：处理`NavCommandQueue`命令、GPS轮询解析、组装`NavState_t`发`NavStateMailbox`、磁力计读取发`MagDataMailbox`，同步置位`HOME_VALID`/`MAG_OK`两个EventGroup bit。
- **开机自动搜星**：不依赖外部命令触发，主循环里每轮检查`s_home_valid`，未成功则持续重试`GPS_SetHome()`，成功后不再重试。`NavCommandQueue`保留给以后需要外部显式触发重新记录Home点的场景用。
- `GPS_SetHome()`成功条件：`gps_fix_type >= 1` 且 `gps_satellites >= 4`。
- 经纬度以`int32_t`定点整数存储（1e-7°单位），全程不经过float中间态，`NavState_t`赋值时**不做任何额外缩放**，直接赋值。
- **`MAG_OK`判据**：I2C读取成功 && 状态寄存器0x09的**OVFL位**（任一轴溢出）未置位，两者都满足才判OK。QMC5883自检功能（0x0B寄存器SELF_TEST位）不用于运行时持续检测——自检会让芯片跳出Continuous Mode进入Suspend，测完需要重新配置才能恢复连续输出，跟20ms周期的持续采集需求冲突，只适合开机一次性诊断（当前未接入，留待专门的QMC自测环节）。
  - OVFL的"±30000 LSB"判据跟当前配置量程绑定，不是int16硬件上限：四档量程(±30G/±12G/±8G/±2G)乘各自灵敏度都恰好等于30000，当前配置是±8G（`0x0B`写`0x08`），OVFL置位即代表实测磁场强度超过±8G。

## 十一、黑匣子（`bsp_blackbox.c` + `app_blackbox.c`，已实现，未上板验证）

从最初的`blackbox.c/h`（旧架构风格，单一帧结构体+直接依赖`ff.h`）重构为bsp层模块，只暴露纯HAL/stdint接口，内部帧结构体完全私有，不需要`CopyTo`。

**帧格式**：每条记录 = `[MAGIC(1B)=0xAA][type(1B)][...内容...]`，全字段小端。MAGIC是帧同步头，供上位机解析器丢失同步后（如写入中掉电导致某条记录损坏）逐字节向后扫描重新定位，代价是每条记录多1字节。

- `BB_REC_MOTION`(0x01)：高频运动帧，21字节 = MAGIC+type+time_ms(2)+angle_cdeg[3]（0.01°定点）+motor[4]+target_cdeg[3]，每控制周期（**仅Armed状态下**）调用一次
- `BB_REC_ARM_CHANGED`(0x02)：5字节，ARM状态跳变时记
- `BB_REC_DUAL_FAULT`(0x03)/`BB_REC_VOLTAGE_FAULT`(0x04)：4字节，跳变沿记一次，不重复
- `BB_REC_IMU_SWITCH`(0x05)：5字节，正常切换IMU时记

**双缓冲+信号量驱动**：`Task_Blackbox`（`app_blackbox.c`）替换旧代码那种裸机WFI忙等的写法，`BB_WaitReady`（超时50ms）+ `BB_Process`排空READY缓冲。

**文件生命周期跟ARM状态绑定，懒加载**：

- `Task_Blackbox`开机**不**自动挂载/建文件，纯阻塞等`BB_PollControlRequest`收到`BB_CTRL_NEWFILE_REQ`才第一次调用`BB_Init()`。
- `app_arm.c`在Disarmed→Armed瞬间调`BB_RequestNewFile()`（非阻塞，只置事件位）；Armed→Disarmed（含紧急disarm）瞬间调`BB_RequestClose()`。
- 真正的`f_mount`/`f_open`/`f_close`阻塞式SD卡操作全部在`Task_Blackbox`里做，`app_arm.c`所在的`Task_FlightCtrl`不会被I/O卡住。
- `BB_LogMotion`只在`g_arm_state==ARM_STATE_ARMED`时调用，Disarmed期间不写，避免往已关闭的文件句柄写数据。

**关键内部对象，创建时机分两处，不能合并**：

- `s_dataReadySem`（数据就绪信号量）：`BB_BufferInit()`里创建，每次开新文件都会调用，加了`if(NULL)`保护避免重复创建泄漏对象。
- `s_ctrlEvt`（控制请求事件对象，`BB_RequestClose`/`BB_RequestNewFile`/`BB_PollControlRequest`依赖它）：**必须独立于`BB_BufferInit`提前创建**，由`BB_ControlInit()`负责，在`App_Blackbox_Task`一开始、进入等待循环前调用一次。**这是一个真实踩过的坑**：如果`s_ctrlEvt`的创建被放进`BB_BufferInit()`，会形成死锁——`BB_RequestNewFile()`要给它置位，但它要等`BB_Init()`成功后才被创建，而`BB_Init()`又要等`BB_RequestNewFile()`触发才会被调用，信号永远丢进一个不存在（`NULL`）的对象里。

**上位机解析**：`bb_parser.py`按MAGIC字节定位记录边界，丢失同步会逐字节重新扫描并统计`resync_count`（应为0）。

**IndicatorEventQueue接入**：SD写入出错（`BB_GetErrorFlags()`非0，缓冲溢出或写入失败）跳变沿发`EVT_SD_CARD_ERROR`，在`app_blackbox.c`里判断（不在`bsp_blackbox.c`里，遵守bsp层不碰app级共享资源的分层原则）。

**未解决**：`fc`结构体的撕裂读保护仍未处理（`FlightControl_CopyTo`目前是整体赋值，无临界区），`app_telemetry.c`还没写，目前没有调用方，先留着。SD卡DMA传输问题已解决（见"十五、内存布局与DMA安全"），黑匣子已能正常建立文件并写入。

## 十二、SD卡底层驱动（`bsp_sdcard.c` + `user_diskio.c`）

**握手**（`BSP_SD_Init`）：CMD0→CMD8→ACMD41→CMD58标准流程，SPI2初始化低速（CubeMX默认预分频）。握手成功后调`BSP_SD_SetSpeedFast()`——运行时用`HAL_RCC_GetPCLK1Freq()`动态算出不超过2.625MHz（旧架构裸机实测验证过的安全上限）的最高预分频档位，不硬编码具体数值。已核实：APB1实际频率42MHz，`BSP_SD_SetSpeedFast()`算出的预分频档位为÷16，实际SPI2时钟2.625MHz，与设计值完全一致，时钟树配置本身没有问题。

**已修复的四个真实bug**（均已验证生效）：

1. **`diskio.c`的`disk_initialize`标志位锁死bug**（ST官方生成代码本身的问题，不是本项目引入的）：原代码`is_initialized[pdrv]=1`在调用真正的`USER_initialize()`**之前**就无条件执行，导致只要第一次握手失败，这个标志位永久锁死为"已初始化"，之后所有重试全部被短路。**修复**：只有真正握手成功（`!(stat & STA_NOINIT)`）才置位`is_initialized[pdrv]`。⚠️**这个文件如果CubeMX重新生成代码会被覆盖，需要记得重新打补丁**（`USER CODE`保护区机制不覆盖FatFS中间件文件，CubeMX重新生成时会整份覆盖`ff.c`/`diskio.c`，不会保留手动补丁）。
2. **`user_diskio.c`是从未被填写过的空骨架**：`USER_read`/`USER_write`原本直接`return RES_OK`，压根没碰过真实数据；`USER_status`每次都无条件重置成`STA_NOINIT`；`USER_ioctl`对所有命令一律返回`RES_ERROR`。已全部接到`BSP_SD_Init`/`BSP_SD_ReadBlock`/`BSP_SD_WriteBlock`。
3. **CMD0/CMD17/CMD24重试循环原本完全没有延时**（10/200/200次紧密轮询，中间无间隔）。经实测确认：这张卡在命令被拒绝后需要**真实流逝的时间**才能让内部状态机自行恢复，不是"多打几次指令"能解决的。已在这三个循环里加`osDelay(2)`，握手最开始也加了`osDelay(10)`。
4. **DMA全双工传输scratch buffer误落CCM RAM导致约10秒超时**（详见"十五、内存布局与DMA安全"），已通过scatter文件+`#pragma`分区修复并验证。

**寻址**：`s_sdCardType`区分SDHC（block直接寻址）/SDSC（`block*512`字节寻址），由CMD58的OCR寄存器bit30判定。

**`SD_SPI_DMA_Transceive`（DMA版本）目前是正式启用的读写路径**。等效的阻塞式版本`SD_SPI_Blocking_Transceive`此前作为止血方案存在，问题解决后应确认已清理，见"十七、待办/未接项清单"。

## 十三、提示系统（Buzzer/LED/`app_indicator.c`）

**硬件层**（`bsp_buzzer.c`/`bsp_led.c`）：纯执行接口，`BSP_Buzzer_On/Off`、`BSP_LED_On/Off/Toggle`，不做判断。

**`app_indicator.c`把`IndicatorEventQueue`里的事件翻译成蜂鸣器+LED同步节拍**，三档优先级（`NOTICE`<`WARNING`<`CRITICAL`），只有严格更高优先级才能打断当前播放的节拍，优先级不够就塞回队列尾部等这轮播完。节拍定义用`switch`按事件名字分发（不用数组下标查表——数组版本试过，armcc对C99指定初始化器`[EVT_XXX]=...`支持不完整会编译失败，改用普通数组又有顺序脆弱性风险，最终定案用`switch`，靠事件名字绑定，不依赖枚举声明顺序）。

**持续报警机制**：`EVT_RC_LOST`/`EVT_CRITICAL_BATTERY`/`EVT_IMU_FAULT`这三个安全关键事件，只要故障状态持续存在，生产端就按固定间隔（略大于对应节拍自身播放时长，留出静默间隙）重新入队，不是单次提示；其余事件（`ARMED`/`DISARMED`/`GPS_FIX_ACQUIRED`/`LOW_BATTERY`/`SD_CARD_FULL`/`SD_CARD_ERROR`）跳变沿只响一次。

**`IndicatorEventQueue`生产端接线情况**：

- `EVT_ARMED`/`EVT_DISARMED`：`app_arm.c`，跟`BB_LogArmChanged`同处
- `EVT_RC_LOST`：`app_rc_link.c`，`link_ok`持续为false期间按2500ms重发
- `EVT_GPS_FIX_ACQUIRED`：`app_nav.c`，`s_home_valid`首次0→1跳变
- `EVT_LOW_BATTERY`：`app_power_monitor.c`，独立14.0V预警阈值（跟触发disarm的13.2V是两回事），带0.2V迟滞
- `EVT_CRITICAL_BATTERY`：`app_power_monitor.c`，`voltage_fault`持续为true期间按1000ms重发
- `EVT_IMU_FAULT`：`app_imu2_redundancy.c`，`dual_fault`持续为1期间按900ms重发
- `EVT_SD_CARD_ERROR`：`app_blackbox.c`，见"十一"
- `EVT_SD_CARD_FULL`：**没有生产端**——当前没有任何模块检测SD卡剩余容量，枚举值定义了但触发不了，是明确的待办项，不是遗漏

## 十五、内存布局与DMA安全

STM32F405拥有两块物理独立的SRAM：一块112KB挂在AHB Bus matrix-S上（地址`0x20000000`起，SRAM1），所有Bus Master（CPU、DMA1、DMA2等）都能通过总线矩阵访问；另一块64KB是CCM data RAM（地址`0x10000000`起），**直接点对点连接到Cortex-M4内核的D-bus，完全不接入Bus matrix-S**（RM0090第2.1节Figure 1系统架构图 + 2.3.1节"Embedded SRAM"）。**任何Bus Master（包括DMA1、DMA2）在物理拓扑上都无法访问CCM，这是芯片设计层面的硬限制**。

**当前的分区规则**（`MDK-ARM/CubeMX_Create/CubeMX_Create.sct`）：

```
RW_IRAM1 0x20000000 0x00020000  {  ; SRAM，默认落点 + 显式标记的DMA安全buffer
   .ANY (+RW +ZI)
   *(DMA_SAFE_SRAM)
}
RW_IRAM2 0x10000000 0x00010000  {  ; CCM，只收显式标记内容，不再默认开放
   *(DMA_UNSAFE_CCM)
}
```

普通变量默认落SRAM（`RW_IRAM1`的`.ANY`兜底），CCM变成"opt-in专区"，不会再有变量意外落入。

**已知会被DMA访问、显式标记为`DMA_SAFE_SRAM`的buffer**：

| Buffer | 所在文件 | 用途 |
| --- | --- | --- |
| `s_sdTxDummy` | `bsp_sdcard.c` | SD卡DMA全双工读取时的TX填充源 |
| `s_sdRxSink` | `bsp_sdcard.c` | SD卡DMA全双工写入时的RX丢弃桶 |
| `s_dshot_buf` | `bsp_dshot.c` | DSHOT TIM1 burst DMA源缓冲区 |

标记方式（armcc）：

```c
#pragma arm section zidata = "DMA_SAFE_SRAM"
static uint8_t s_sdTxDummy[512];
static uint8_t s_sdRxSink[512];
#pragma arm section zidata          // 恢复默认，后面的变量不受影响
```

**以后新增任何会被DMA（或其他非CPU的Bus Master，如以太网DMA、DMA2D）读写的buffer，必须显式加上这个标记**，不能依赖链接器的默认打包行为——链接器不理解"这个变量会被DMA访问"这层C语言语义，只会按内存布局机械打包，工程里增删任意源文件都可能让打包结果重新洗牌，不加标记就无法保证这个buffer不会在某次编译后意外落入CCM。

**Keil工程设置**：`Options for Target → Linker`页签，`Use Memory Layout from Target Dialog`已取消勾选，改为显式指定Scatter File路径——否则Keil会在每次编译时根据Target页签的IROM/IRAM设置自动重新生成`.sct`，覆盖掉这里的手工分区。

**ELRS（`s_dma_rx_buf`）、GPS（`gps_dma_buf`）、黑匣子（`s_buf`）这几个已有的DMA相关buffer经核实均落在SRAM1，不受此问题影响，不需要额外标记。**

## 十六、已知重大问题

### 16.1 SD卡DMA传输超时 —— ✅已解决，见"十五、内存布局与DMA安全"

根因是`bsp_sdcard.c`的DMA全双工scratch buffer（`s_sdTxDummy`/`s_sdRxSink`）以及`bsp_dshot.c`的DSHOT输出buffer（`s_dshot_buf`）被链接器意外分配到CCM RAM——DMA物理上无法访问CCM，导致传输长期停滞，最终由软件层5秒超时兜底返回，表现为约10秒的调用耗时（含前段约5.1秒的异常缓慢时钟活动+后段约5秒的完全静默）。已通过scatter文件重新分区+源码显式`#pragma`标记两层手段修复，重新烧录验证DMA全双工传输不再超时，黑匣子已能正常建立文件并写入。
